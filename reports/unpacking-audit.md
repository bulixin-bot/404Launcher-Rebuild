# 404Launcher 1.3.9 独立静态恢复审计

审计日期：2026-10-25。审计对象是 1.3.9 原始文件及其恢复包，详细计数、哈希、PE 信息与对照结果见同目录 `unpacking-audit.json`。本报告不运行原启动器、业务 DLL 或 `.pyd`，不修改登录、授权或时长逻辑。

**结论：PyInstaller 外层归档已成功提取，Python 入口和部分 .NET 后端可读、可编译；现有证据不足以宣称“完全脱壳”，也没有恢复为能从全部源码独立重建的完整启动器。** Cython 编译本身不等于额外加壳，不能仅因保留 `.pyd` 就断言仍有某种特定壳。

## 7 个业务原生模块

`app_updater`、`auth_client`、`dotnet_bridge`、`game_launcher`、`gui`、`official_4399_sdk`、`sauth4399_client` 全部仍是 Windows x64 PE32+ 原生 `.pyd`，没有 CLR 元数据头，含各自 `PyInit_模块名` 导出及 Cython 标记。恢复包里的 7 个文件逐字节等于原包文件；两个 PYZ 中没有这些同名业务模块，恢复树中也没有对应 `.py`、`.pyx` 或 `.pyc`。

这些文件均没有 `UPX` 节名，但节名、熵及字符串只是有限静态信号，不足以排除所有打包、虚拟化、加密或反篡改机制。本次没有进行完整原生反汇编、运行时解密验证或可重建的原生源码恢复。

## .NET 元数据与反编译残留

原 `404NEL.dll` 存在一组重复嵌套类型名，以及 251 个名为 `<>c` 的特殊字段。已有修复映射共重命名 502 个元数据条目。独立 PEReader 检查确认原版和元数据修复副本均有 350 个类型、1,083 个字段、899 个方法，899 个方法体均可读取；修复副本中上述重复名与特殊字段名已消除。

`Schedule-Acquire-Initialize.Resolve.cs` 在原始反编译树及机械修复树中各有 **251 处** `Not supported: data(...)` 注释。不能据此直接断言丢失了 251 份数据：本次逐项复核发现，旁边恢复的 251 个 `byte[]` 字面量，均与注释中的长度及字节一致，也全部与原 DLL 相应字段的 RVA 数据长度及 SHA-256 一致。原版与元数据修复副本的全部 253 份 RVA 字段数据，其长度和哈希的多重集合也完全一致。

`MemoryOptimizer.cs` 的 `GetCommandLine` 方法仍保留 **4 行** ILSpy `Unknown result type` / `Expected Obj, but got Unknown` 注释。已有恢复说明将其关联到缺失的 `System.Management` 引用，且机械修复树能编译；仍不能仅凭编译通过证明该路径的实际行为等价。

元数据写回会重排方法和字段 token，所以按同一个数字 token 比较两版原始 IL 字节不是有效的语义等价检验。`unpacking-audit.json` 保留了这个对照及其限制；本报告没有把 token 差异当作逻辑已改变的证据，也没有声称所有 .NET 方法语义均已证明等价。

## 审计边界

本次使用标准 PE/CLR 数据读取、PyInstaller 归档解压、Python 3.12 marshal 解析和 compile-only 比较；未导入执行业务模块。审计只证明上述局部数据与来源、语法及字节码比较结果。完整应用仍需 7 个原生模块的源码或可维护替代实现、完整打包配置及集成测试，才可支持“从源码独立重建完整启动器”的结论。
